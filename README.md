# Ржавый чат

Простой чат на WebSocket: самостоятельный сервер на Rust и SPA-клиент на Vue 3 + TypeScript.

- **Сервер:** Rust, axum 0.8, tokio, `broadcast`-каналы, sqlx + PostgreSQL, без `unsafe`.
- **Клиент:** Vue 3 (Composition API), Vite, TypeScript.
- **Транспорт:** JSON-сообщения поверх WebSocket: общий канал `# general` и личные переписки один-на-один.
- **Хранение:** аккаунты, сессии, публичная история, личные сообщения и отметки о прочтении — в PostgreSQL.

## Что уже умеет

- регистрация и вход по имени и паролю; пароли хранятся только как Argon2id-хеши;
- долгоживущие сессии: токен сохраняется в браузере, вход восстанавливается после перезагрузки;
- выход из аккаунта отзывает сессию на сервере;
- смена пароля прямо из интерфейса: остальные сессии аккаунта после неё отзываются;
- один аккаунт может быть открыт в нескольких окнах: имя в списке участников не дублируется,
  а личные сообщения приходят в каждое окно;
- ограничение частоты попыток входа и регистрации по IP-адресу (`429 Too Many Requests`);
- проверка `Origin` при апгрейде WebSocket: чужой сайт получает 403;
- общая комната и список участников онлайн;
- рассылка сообщений всем подключённым;
- личные сообщения между двумя участниками: доставляются только адресату и автору;
- системные уведомления о входе и выходе;
- последние 100 сообщений выдаются новому участнику;
- история переживает перезапуск сервера: при входе восстанавливаются и общий канал,
  и личные диалоги вместе со счётчиками непрочитанных;
- сообщения и отметки о прочтении привязаны к аккаунтам по UUID, а не к именам;
- heartbeat (ping/pong) для обнаружения мёртвых соединений;
- серверная валидация имени, пароля и текста;
- интерфейс: отдельная лента для каждого диалога, счётчик непрочитанных, индикатор «в сети / не в сети» у собеседника;
- `GET /api/health` для проверки состояния;
- в production Rust-сервер сам раздаёт собранный фронтенд;
- корректное завершение по Ctrl+C / SIGTERM.

## Подготовка PostgreSQL

Сервер работает только с базой и без неё не стартует. Достаточно создать саму базу —
таблицы `accounts`, `sessions`, `chat_messages`, `direct_messages` и `direct_reads`
сервер создаёт сам при каждом запуске, применяя миграции по порядку
(`migrations/001_init.sql`, затем `002_account_ids.sql`; все команды идемпотентны).

```powershell
# через psql (понадобится пароль пользователя, которому разрешено создавать базы)
psql -U postgres -c "CREATE DATABASE rust_chat ENCODING 'UTF8'"

# то же самое можно сделать из pgAdmin или любой другой оболочки SQL
```

Пароль нигде в репозитории не хранится — строка подключения приходит из `CHAT_DB_URL`.

## Запуск в режиме разработки

Нужны Rust (stable), Node.js 20.19+ / 22.12+ и PostgreSQL.

```powershell
# терминал 1 — сервер
$env:CHAT_DB_URL = "postgres://<user>:<password>@localhost:5432/rust_chat"
cargo run
```

```bash
# терминал 2 — клиент с горячей перезагрузкой
cd frontend
npm install
npm run dev
```

Откройте <http://localhost:5173>. Vite проксирует `/ws` и `/api` на
`http://127.0.0.1:3000`, поэтому CORS не нужен.

## Сборка и запуск production

```bash
cd frontend
npm install
npm run build

cd ..
cargo run --release
```

Откройте <http://localhost:3000> — сервер раздаёт `frontend/dist` и
WebSocket на том же адресе.

| Переменная | Где | По умолчанию | Назначение |
| --- | --- | --- | --- |

| `VITE_WS_URL` | клиент | same-origin `/ws` | явный URL WebSocket |

Пример для PowerShell:

```powershell
$env:CHAT_DB_URL = "postgres://<user>:<password>@localhost:5432/rust_chat"
$env:CHAT_BIND = "127.0.0.1:8080"
$env:RUST_LOG = "rust_chat=debug"
cargo run
```

Сервер без `CHAT_DB_URL` не стартует и подсказывает, что задать. Если база недоступна,
в логе будет причина (неверный адрес, пароль или несуществующая база).

## Работа за reverse proxy (TLS)

Чтобы чат работал по HTTPS, проще всего поставить перед сервером reverse proxy:
он терминирует TLS и отдаёт запросы бэкенду по HTTP. Сам сервер при этом
никакие сертификаты не принимает.

Nginx (упрощённо):

```nginx
server {
    listen 443 ssl;
    server_name chat.example.com;

    # ssl_certificate / ssl_certificate_key ...

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;

        # Обязательно для WebSocket.
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Токен сессии передаётся в query-параметре: не пишите полный URL в логи.
        access_log off;
    }
}
```

Caddy (минимальный):

```caddyfile
chat.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

После поднятия прокси важно учесть:

- в браузере сайт открывается с `https://`, значит WebSocket идёт по `wss://` —
  клиент подставляет схему сам;
- если прокси переписывает заголовок `Host` на адрес бэкенда, добавьте публичный
  адрес в `CHAT_ALLOWED_ORIGINS=https://chat.example.com`, иначе апгрейд
  WebSocket будет отклонён с 403;
- чтобы лимиты попыток считались по реальному IP посетителя, а не по адресу
  прокси, включите `CHAT_TRUST_PROXY=true` (только если сервер недоступен напрямую);
- внешний порт `3000` лучше закрыть: поднимайте сервер на `CHAT_BIND=127.0.0.1:3000`.

## Аккаунты и API

Вход выполняется по HTTP, после чего клиент подключается к WebSocket с токеном сессии.

| Метод | Путь | Тело / заголовок | Ответ |
| --- | --- | --- | --- |
| `POST` | `/api/register` | `{ "username": "Алиса", "password": "..." }` | `{ "token": "...", "user": { "id": "...", "username": "Алиса" } }` |
| `POST` | `/api/login` | то же | то же |
| `GET` | `/api/me` | `Authorization: Bearer <token>` | `{ "id": "...", "username": "Алиса" }` |
| `POST` | `/api/logout` | `Authorization: Bearer <token>` | `204 No Content` |
| `POST` | `/api/password` | `{ "current_password": "...", "new_password": "..." }` + `Authorization: Bearer <token>` | `204 No Content` |

- имя — 2–24 символа, сравнивается без учёта регистра и должно быть уникальным;
- пароль — от 8 до 128 символов, хранится как Argon2id-хеш;
- токен сессии живёт 30 дней, в базе хранится только его SHA-256;
- после смены пароля все остальные сессии аккаунта отзываются, текущая остаётся;
- `/api/login` ограничен 10 попытками в минуту с одного IP, `/api/register` — 5 попытками
  за 10 минут; при превышении сервер отвечает `429` и заголовком `Retry-After`;
- один аккаунт может держать несколько WebSocket-соединений (несколько окон браузера).

## Протокол

Эндпоинт: `ws://<host>/ws?token=<токен сессии>`. Все сообщения — JSON с полем `type`.
Соединение без действующей сессии отклоняется с HTTP 401, а с чужим `Origin` —
с HTTP 403; оба случая происходят ещё до апгрейда.

Клиент → сервер:

```json
{ "type": "message", "text": "Привет!" }
{ "type": "direct", "to": "Боб", "text": "Только между нами" }
{ "type": "read", "peer": "Боб" }
```

Сервер → клиент:

| `type` | Поля | Когда приходит |
| --- | --- | --- |
| `welcome` | `you`, `users` | сразу после подключения |
| `history` | `messages` | сразу после `welcome` |
| `direct_history` | `threads` | после `history`, если у пользователя есть сохранённые диалоги |
| `message` | `message` | новое сообщение в чате |
| `direct` | `message` | личное сообщение (только автору и адресату) |
| `system` | `text`, `at` | вход/выход участника |
| `users` | `users` | изменился список онлайн |
| `error` | `message` | ошибка валидации/входа |
| `session_ended` | `reason` | сессия отозвана, например после смены пароля на другом устройстве |

Пример личного сообщения:

```json
{
  "type": "direct",
  "message": {
    "id": "7b2f4c90-...",
    "from": "Алиса",
    "to": "Боб",
    "text": "Только между нами",
    "sent_at": "2026-11-03T18:02:11.094331Z"
  }
}
```

Пример восстановления диалога после входа:

```json
{
  "type": "direct_history",
  "threads": [
    {
      "peer": "Боб",
      "unread": 1,
      "messages": [
        {
          "id": "7b2f4c90-...",
          "from": "Алиса",
          "to": "Боб",
          "text": "Только между нами",
          "sent_at": "2026-11-03T18:02:11.094331Z"
        }
      ]
    }
  ]
}
```

Пример сообщения чата:

```json
{
  "type": "message",
  "message": {
    "id": "0e5f1a7c-...",
    "author": "Алиса",
    "text": "Привет!",
    "sent_at": "2026-11-03T17:44:50.224891Z"
  }
}
```

Ограничения:

- имя — от 2 до 24 символов, буквы/цифры/пробел/`_`/`-`, без учёта регистра
  проверяется на уникальность;
- пароль — от 8 до 128 символов;
- текст сообщения — до 2000 символов, непустой после `trim`;
- личное сообщение можно отправить только участнику, который сейчас в сети, и нельзя — самому себе;
- у одного аккаунта может быть открыто несколько окон; личное сообщение получает каждое из них;
- токен сессии передаётся в query-параметре WebSocket, поэтому URL не стоит писать в логи reverse proxy;
- размер WebSocket-фрейма ограничен 16 КиБ;
- в памяти держится последние 100 сообщений общего канала, в базе сохраняются все;
- при входе возвращается не больше 100 последних сообщений на один диалог.

## Как это устроено

**Одна задача tokio на соединение.** `ws.rs` через `tokio::select!` одновременно
читает входящие кадры, получает события из `broadcast`-канала, разбирает свою
личную `mpsc`-очередь и раз в 30 секунд отправляет ping. Медленный клиент не
блокирует остальных: при переполнении буфера `broadcast` он получает `Lagged`,
пропускает старые события и продолжает.

**Хранение в PostgreSQL.** `db.rs` держит пул `sqlx` и пять таблиц:
`accounts` (аккаунты), `sessions` (сессии входа), `chat_messages` (общий канал),
`direct_messages` (личные переписки) и `direct_reads` (сколько диалога уже прочитано).
Сообщения ссылаются на аккаунты по `account_id`, а не по имени: имя хранится
только в `accounts` и подтягивается при чтении, поэтому переименование
пользователя не разорвёт его историю. У сообщений каждой строки есть `seq` —
монотонный номер вставки, по нему и восстанавливают порядок после перезапуска,
не полагаясь на метку времени. Схема из `migrations/` применяется при каждом
старте и идемпотентна: сервер поднимается и на пустой, и на уже наполненной базе.
`002_account_ids.sql` при первом запуске переносит базы, созданные до этого
перехода: находит аккаунты по старым именам и удаляет только те сообщения,
автора которых восстановить невозможно.

**Аутентификация.** Пароль хешируется Argon2id в `spawn_blocking`, чтобы не
блокировать async-рантайм. При входе сервер создаёт случайный 256-битный токен,
хранит его SHA-256 в `sessions` и отдаёт сам токен клиенту. WebSocket принимает
токен в query-параметре (браузерный API не умеет задавать заголовки) и проверяет
сессию до апгрейда; имя автора берётся из аккаунта, а не из сообщения клиента.
Смена пароля требует текущий пароль, сохраняет новый Argon2id-хеш и удаляет все
сессии аккаунта, кроме той, с которой пришёл запрос. Открытые WebSocket-соединения
других устройств получают `session_ended` и закрываются, а не продолжают работать
со старым входом.

**Лимиты попыток.** `rate_limit.rs` хранит скользящее окно попыток по IP:
10 входов в минуту и 5 регистраций за 10 минут. Лимит проверяется до дорогого
Argon2, поэтому перебор не занимает рабочие потоки. За reverse proxy реальный
адрес берётся из `X-Forwarded-For`, но только при `CHAT_TRUST_PROXY=true`:
без этого флага заголовок подделывается и защита обходится.

**Сначала запись, потом доставка.** Личное сообщение попадает в базу до того,
как уйдёт получателю, публичное — сразу после публикации в памяти. Так
восстановленный после переподключения диалог не может «забыть» сообщение,
которое клиент уже видел.

**Прочитанное считается на сервере.** Клиент шлёт `read` для открытого диалога,
сервер запоминает `last_seq` пары и при входе возвращает число сообщений
свежее этой отметки. Поэтому счётчик непрочитанных переживает перезагрузку
вкладки.

**Регистр имён.** Имена сравниваются без учёта регистра в списке онлайн
и при поиске собеседника: за это отвечает `name_key`. В базе имени больше нет —
`chat_messages.author_id`, `direct_messages.sender_id`/`recipient_id` и
`direct_reads.user_id`/`peer_id` ссылаются на `accounts.id`, поэтому диалог
не зависит ни от регистра, ни от будущего переименования аккаунта.

**Личные сообщения идут мимо broadcast.** Каждое соединение при входе отдаёт
в `ChatState` свой `mpsc::Sender`. `connections` находит все окна адресата по имени
(регистронезависимо), и `send_to` кладёт событие в очередь каждого из них, а
автору сервер делает эхо в текущий сокет (и в его другие окна) — содержимое
переписки не попадает в общий канал и не видно другим участникам. Очередь
ограничена 64 событиями: если получатель не успевает, отправка возвращает
ошибку вместо раздувания памяти.

**Общее состояние без лишних блокировок.** `ChatState` — дешёвая в клонировании
обёртка над `Arc<Inner>`. Пользователи и история защищены `tokio::sync::RwLock`,
а рассылка идёт через `broadcast::Sender`. Сообщение сохраняется в историю и
публикуется под одним замком, поэтому порядок истории и порядок доставки
совпадают даже при одновременной отправке из разных соединений.

**Типы вместо повторных проверок.** Входящие имя и текст парсятся в newtype-ы
`UserName` и `MessageText`. Дальше по коду уже невозможно передать
невалидированное значение — проверка происходит ровно один раз, на границе.

**Ограниченная история.** `VecDeque` хранит не больше 100 сообщений; старые
вытесняются автоматически, но остаются в базе.

## Тесты

```bash
cargo test
```

Покрыты валидация имён, паролей и текста, хеширование и проверка паролей,
уникальность токенов, проверка `Origin` для WebSocket-апгрейда, распознавание IP
за прокси, лимиты попыток по скользящему окну, несколько окон одного аккаунта,
сортировка/удаление пользователей, доставка личных сообщений адресату, отказ
неизвестным пользователям и ограничение истории. Эти тесты работают с
состоянием в памяти и не требуют базы.

Интеграционный тест с настоящим PostgreSQL помечен `#[ignore]`:

```powershell
$env:CHAT_DB_URL = "postgres://<user>:<password>@localhost:5432/rust_chat"
cargo test -- --ignored
```

Он проверяет восстановление публичной истории, склейку диалога по паре
`account_id`, счётчик непрочитанных и отметку о прочтении. Тест сам создаёт
аккаунты и очищает таблицы (`TRUNCATE ... RESET IDENTITY`), поэтому запускайте
его на отдельной тестовой базе, а не на рабочей.

Клиент проверяется сборкой:

```bash
cd frontend
npm run build
```
